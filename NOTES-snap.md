# Snap to Today (photo / screenshot → tasks, events, bills)

## Where things are

- **Entry points**: the image button beside the capture box (`components/Capture.tsx`, `onSnap`: "Take a photo" / "Choose a picture") and Android **Share → Today** with pictures (`AndroidManifest.xml` SEND + SEND_MULTIPLE `image/*`, `TodayNativePlugin.parse()` → launch intent `kind: "images"`, handled in `components/App.tsx` next to the text-share handler). The sheet is `components/SnapSheet.tsx`, loaded with `next/dynamic` the first time it is used (its own chunk, nothing at start-up).
- **Phone side (Java)**: `SnapNative.java` (EXIF-upright decode, at most 1600 px, JPEG 0.8 kept in memory under a handle, ML Kit text recognition v2 with the **bundled** Latin model, temp-file cleanup, on its own thread) and four methods in `TodayNativePlugin.java`: `snapPick` (camera → a temp file in the app cache, or the photo picker), `snapRead`, `snapJpeg`, `snapRelease`. JS side of the bridge: `lib/nativeBridge.ts` (`snapPick`, `snapRead`, `snapJpeg`, `snapRelease`).
- **Pure logic (`lib/snap/`)**: `clean.ts` (C: remove status bar / keyboard / app buttons / chat times), `extract.ts` (D: classify, dates and times with chrono `en.GB`, roles from the words in front, title / place / amount / reference, lists, chat-style text through the app's own `parseCapture`), `sensitive.ts` (the guard + masking), `gemini.ts` (E: strict schema, prompt, one call), `merge.ts` (validation + field-by-field merge), `dup.ts` (duplicate check), `run.ts` (one run: pictures one by one, offline first, Gemini in the background, cancel, release), `create.ts` (saving: `addFixedEvent` / `finalize` + `addTask`), `deps.ts` (the real phone + Gemini), `settings.ts` ("never send the picture"), `demo.ts` (dev only, `?snapdemo=…`).
- **Reused, not rewritten**: `parseCapture` + `promoteEvent` (chat-style lines, Hinglish via `normalizeHinglish`), `parseShared` (the Pinnacle-style staffing booking), `callGemini` (key in local storage, model discovered from Google's list, timeout), `finalize` (learned fixes, area guess, a sensible slot), `actions.addFixedEvent` / `addTask`, the sync pipeline (reminders, widget, backups, "Today – Plan" copy, phone-calendar write all run from `commit`).
- **Data**: `FixedEvent.location` and `.notes` (written to the phone calendar's location and description), `ItemSource "snap"` (kept in `backup.ts` `SOURCES`; not in `AUTO_SOURCES`, so it is never listed in "What the app did"). No data-version bump: every new field is optional and `migrate` keeps them.
- **Tests**: `tests/snap-extract.test.ts` (69 fixtures), `tests/snap-merge.test.ts` (garbage Gemini answers, validation, merge), `tests/snap-flow.test.ts` (run, privacy, cancel, creation through the store).

## Judgement calls

- **Shift offers are tasks** in Side work (as asked), timed when a start time was read. The card's Event / Task / Bill / Note switch turns one into a fixed event.
- **A one-off bill is a task**, "Pay <name> (£amount)", due on its due date, in Finance (else Life). `Bill` in the app is only a repeating schedule with no amount, so a one-off bill does not fit it; the existing check-in reminder on the due day applies. If the title matches one of your repeating bills the card says its reminders already exist.
- **Dates and times**: documents use chrono's **`en.GB`** (03/11/2026 is 3 November). chrono's UK parser reads "Nov 14" (month first, as tickets write it) as *November 2014*, so `dayFirst` turns "Nov 14" into "14 Nov" first. Chat-style lines go through the app's capture parser, which reads a bare `03/11/2026` the American way, so `ukDates` writes numeric dates out ("3 November 2026") before it sees them. (Typed capture itself is unchanged and still reads `03/11/2026` as 11 March: that was already so.) A date that only works the American way (month 13) is read that way and marked unsure.
- **A time zone label is dropped, not converted**: "9:00 PM GMT" on 31 Oct is 21:00 on the phone's clock. The one exception is a staffing booking in the Pinnacle email layout, which the existing share reader handles (it treats GMT as London winter time).
- **Day-of-week and relative words count from the day the picture was taken** (EXIF date, else the file's date, else now). A future "taken" date (a wrong clock) is ignored. A day that ends up in the past is flagged "check the date" and its confidence is lowered.
- **Ends after midnight** ("9pm – 3am"): the end is dropped and said in the notes ("Ends 03:00 (after midnight)"), rather than put on the wrong day.
- **A bare hour in a chat** ("book at 7.45") with no am/pm is the evening, marked unsure. The Hinglish "5 baje" guess keeps the existing rule and is marked unsure too.
- **Several items in one picture**: a list is split when it has more than one distinct full date, one per line (title above or beside each date). A bare weekday in a title ("FRIDAY NIGHT LIVE") is not a second day.
- **What may go online** (checked in this order in `run.ts`): no key or offline → nothing; anything sensitive in the text → nothing, not even the picture; otherwise the cleaned text; the picture only if the text was too weak (under 20 letters or low OCR trust) and "Never send the picture" is off. Gemini's answer only fills gaps or replaces a field it is more sure of; a different day or time is never swapped, it is flagged with what Gemini read.
- **Sensitive guard** = a card number that passes the Luhn check, a sort code with an account number, an IBAN (mod-97), a National Insurance number, a passport / licence / ID number, a CVV, or a password / PIN / one-time code next to its label. Values are masked in the text shown, in a saved note and in item fields; no reference number is kept from such a picture.
- **No permission is asked**: the camera app is asked for one picture (no CAMERA permission), the photo picker needs none, and a shared picture comes with its own read grant.
- **Nothing of a picture is kept**: the camera's temp file is deleted the moment it is decoded (and at start-up if a crash left one); a shared or picked picture belongs to the other app and is only read, never copied; the prepared JPEG exists only in memory, only so it can go to Gemini when the text was weak, and is freed when the sheet closes. Nothing is written to the gallery.
- **Release APK** keeps only the two ARM CPU types (`ndk.abiFilters` in the release build type) because ML Kit's text model ships a native library per CPU type. A debug build keeps them all so it runs on the x86 emulator.

## Known limits

- Printed text only, Latin alphabet (ML Kit's bundled Latin model): no handwriting, no Devanagari. Hinglish works when it is written in Roman letters.
- A picture of a table, a calendar grid or a long timetable is read as lines, so it comes out as a note or a few items, not as a grid.
- Typed capture still reads `03/11/2026` the American way (unchanged on purpose).
- An event that runs over several days ("Fri 9 – Sun 11 Jul") is two items, one per written date.

## What was verified, and where

- **Unit / fixture tests** (`npm test`): 77 extractor fixtures (tickets, bills, letters, deliveries, shifts, chat, Hinglish, UK dates, status-bar clock, sensitive data, hostile and very large text), merge against 27 kinds of garbage Gemini answers, the run (offline first, what may go online, cancel, release), and creation through the real store (reminders, reshuffle, backup round trip). Safety behaviours were mutation-checked (removing the sensitive guard, the never-send-picture switch, the edited-item protection, the day/time flag, the release, the "not app activity" source each makes tests fail).
- **On an Android 17 emulator (x86_64, debug build, real ML Kit)**: Share → Today of a ticket, bill, shift list, WhatsApp-style screenshot (status bar clock, battery, keyboard and chat times ignored), a sideways EXIF-rotated JPEG (comes out upright and read), a Hinglish note, a picture with a card number and bank details (read on the phone only, notice shown, nothing sensitive in the card), a blank picture and a corrupt file (calm messages); airplane mode (read fully offline); tapping Add stores the event with its place and notes, source `snap`; the camera temp folder is empty afterwards.
- **Real recogniser output found two bugs the fixtures could not**: a stray accent glued to "£" made a price line taller and it won the title (fixed: stray glyphs are dropped, a price line can never be the title), and "O2" read as "02" (fixed for the well-known O2 venues).
- **Not verified**: the **camera** path end to end (the emulator was too loaded to drive its camera app; the code compiles and is a plain `ACTION_IMAGE_CAPTURE` with a FileProvider temp file); **several pictures in one share** (`SEND_MULTIPLE`, `am start` cannot send a list; the loop that reads them one by one is covered by tests); **Gemini online** (no key was available: the call, schema, merge and every failure path are covered by tests with a fake Gemini); the real photo picker UI. One "Today isn't responding" dialog appeared while the app cold-started on a heavily loaded emulator (system load 15-21, "no focused window"); it did not recur during interaction, but it was not possible to prove it unrelated on an emulator, so please watch app start on the phone.
- One transient "Could not read the text in that picture" appeared once on the 8th picture in a row while Gradle was saturating the emulator's CPU; it did not repeat. The phone side now logs the cause (`adb logcat -s TodaySnap`) and the page retries that error once.

## APK size (release, signed with the same key as every earlier build)

| Build | Bytes | vs before |
|---|---|---|
| Before Snap to Today (`main`) | 3,753,693 | |
| `npm run android:release` (64-bit + 32-bit ARM) | 23,797,124 | +20.0 MB |
| `npm run android:release -- --arm64` | 17,004,035 | +13.3 MB |

What the extra is, uncompressed: ML Kit's text library (about 11.1 MB for 64-bit ARM, 6.8 MB for 32-bit ARM), its bundled model files (about 1.9 MB) and about 2.1 MB of extra code. Release APKs store native libraries uncompressed so the phone can map them directly, which is why the APK is as big as they are. That is the price of a recogniser that is inside the app and works offline from install; an unbundled model that downloads on first use would be far smaller but would not work offline the first time. The copies are in `apk/today-snap-to-today.apk` and `apk/today-snap-to-today-arm64.apk` (the folder is not in git).
